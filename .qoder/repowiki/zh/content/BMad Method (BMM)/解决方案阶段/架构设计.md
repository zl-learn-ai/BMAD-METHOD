## 引言

BMAD方法论中的架构设计工作流是一种重新构想的架构决策制定方式，旨在通过智能对话生成以决策为中心的架构文档，从而在AI代理实施过程中预防冲突。该工作流强调协作式决策、动态版本验证和智能发现，确保架构设计既灵活又一致。

## 架构工作流的八个步骤

BMAD方法论的架构设计工作流包含八个关键步骤，从初始化到完成，确保架构设计的连贯性和可实施性。

### 1. 加载PRD并理解项目上下文

第一步是加载产品需求文档（PRD），并深入理解项目背景。这包括分析功能需求（FRs）、非功能需求（NFRs）以及任何技术约束或依赖关系。通过计数和分类需求，可以评估项目的规模和复杂性。

**关键活动**:
- 提取和分析功能需求
- 识别非功能需求，如性能、安全性和合规性
- 注意提到的技术限制或依赖关系
- 根据需求数量和类别评估项目规模

**文档来源**
- [step-02-context.md](file://src/modules/bmm/workflows/3-solutioning/architecture/steps/step-02-context.md#L53-L108)

### 2. 发现和评估启动模板

第二步是发现相关的启动模板（如create-next-app、create-t3-app等）。此步骤考虑用户体验（UX）需求来选择模板，搜索当前的CLI选项和默认设置，并记录由启动模板做出的决策。剩余的架构决策将围绕启动模板的基础进行。

**关键活动**:
- 基于PRD搜索相关启动模板
- 查找当前CLI选项和默认设置
- 记录启动模板做出的决策
- 围绕启动模板基础做出剩余架构决策
- 将第一个实现故事设为“使用启动命令初始化”

**文档来源**
- [workflow-architecture-reference.md](file://src/modules/bmm/docs/workflow-architecture-reference.md#L76-L80)

### 3. 适应性引导

第三步是根据用户的技能水平调整对话风格。专家用户会得到快速、技术性的讨论，而初学者则会获得教育和保护，避免复杂性。无论用户技能如何，最终都能产生高质量的输出。

**关键活动**:
- 调整对话风格以适应用户技能水平
- 为专家用户提供快速、技术性的讨论
- 为初学者提供教育和保护，避免复杂性

**文档来源**
- [workflow-architecture-reference.md](file://src/modules/bmm/docs/workflow-architecture-reference.md#L34-L39)

### 4. 协作式决策制定

第四步是促进每个关键决策的协作式讨论。呈现选项及其权衡，集成高级启发式方法以探索创新方法，并确保决策一致且兼容。

**关键活动**:
- 促进每个关键决策的讨论
- 呈现选项及其权衡
- 集成高级启发式方法以探索创新方法
- 确保决策一致且兼容

**文档来源**
- [step-04-decisions.md](file://src/modules/bmm/workflows/3-solutioning/architecture/steps/step-04-decisions.md#L49-L318)

### 5. 解决横切关注点

第五步是解决跨多个组件的横切关注点，如日志记录、监控和安全性。这些关注点需要在整个系统中保持一致。

**关键活动**:
- 识别和解决横切关注点
- 确保日志记录、监控和安全性的一致性

**文档来源**
- [workflow-architecture-reference.md](file://src/modules/bmm/docs/workflow-architecture-reference.md#L79-L80)

### 6. 定义项目结构和边界

第六步是定义项目的结构和边界，包括文件组织、模块划分和层结构。这有助于确保代码的可维护性和可扩展性。

**关键活动**:
- 定义文件组织
- 划分模块和层
- 确保代码的可维护性和可扩展性

**文档来源**
- [workflow-architecture-reference.md](file://src/modules/bmm/docs/workflow-architecture-reference.md#L80-L81)

### 7. 设计新颖的架构模式

第七步是设计新颖的架构模式，用于处理独特的或复杂的模式。当PRD中出现没有标准解决方案的概念时，此步骤帮助设计解决方案。

**关键活动**:
- 检测PRD中的新颖概念
- 与用户合作设计解决方案
- 文档化组件交互和数据流
- 使用启发式方法寻找创新解决方案

**文档来源**
- [workflow-architecture-reference.md](file://src/modules/bmm/docs/workflow-architecture-reference.md#L147-L192)

### 8. 定义实现模式以防止代理冲突

第八步是定义实现模式，以防止AI代理在实施过程中做出不同的决策。通过识别可能导致冲突的决策点，确保所有代理遵循相同的模式。

**关键活动**:
- 识别可能导致冲突的决策点
- 定义命名、结构、格式、通信、生命周期、位置和一致性模式
- 确保所有代理遵循相同的模式

**文档来源**
- [workflow-architecture-reference.md](file://src/modules/bmm/docs/workflow-architecture-reference.md#L196-L237)

## 架构决策文档模板

架构决策文档模板（architecture-decision-template.md）定义了架构决策文档的输出格式和内容要求。该模板确保所有关键决策都被记录下来，并且文档结构清晰、一致。

### 模板结构

```markdown
---
stepsCompleted: []
inputDocuments: []
workflowType: 'architecture'
lastStep: 0
project_name: '{{project_name}}'
user_name: '{{user_name}}'
date: '{{date}}'
---

# 架构决策文档

_本文档通过逐步发现的方式协作构建。随着我们逐一解决每个架构决策，各部分将被追加到文档中。_
```

**关键字段**:
- `stepsCompleted`: 已完成的步骤列表
- `inputDocuments`: 输入文档列表
- `workflowType`: 工作流类型
- `lastStep`: 最后完成的步骤
- `project_name`: 项目名称
- `user_name`: 用户名称
- `date`: 日期

- [architecture-decision-template.md](file://src/modules/bmm/workflows/3-solutioning/architecture/architecture-decision-template.md#L1-L14)

## 实际案例分析

### 企业级项目

对于企业级项目，如金融科技（fintech）应用，`domain-complexity.csv` 文件中的信号（如“banking”、“payment”、“trading”）表明这是一个高复杂度项目，建议使用增强型工作流。工作流将重点关注金融安全、PCI合规性、交易算法和欺诈检测。

**关键决策**:
- **数据库选择**: PostgreSQL with Row Level Security
- **支付处理**: Stripe Billing for subscriptions
- **权限系统**: RBAC or ABAC for permissions
- **认证**: NextAuth or Clerk for auth

**文档来源**
- [domain-complexity.csv](file://src/modules/bmm/workflows/3-solutioning/architecture/data/domain-complexity.csv#L3-L4)

### 初创项目

对于初创项目，如社交媒体平台，`domain-complexity.csv` 文件中的信号（如“social network”、“community”、“users”）表明这是一个高复杂度项目，建议使用高级工作流。工作流将重点关注社交图算法、动态排名、通知系统和隐私。

**关键决策**:
- **数据库选择**: PostgreSQL with graph extensions or Neo4j
- **动态缓存**: Redis for feed caching
- **用户搜索**: Elasticsearch for user search
- **通知**: WebSockets for notifications

**文档来源**
- [domain-complexity.csv](file://src/modules/bmm/workflows/3-solutioning/architecture/data/domain-complexity.csv#L5-L6)

## 与分析和实现阶段的衔接

架构设计工作流与分析阶段的输出和实现阶段的需求紧密衔接，确保架构设计的连贯性和可实施性。

### 分析阶段的输出

分析阶段的输出（如产品简报、市场研究、领域研究和技术研究）直接输入到规划阶段。这些输出为架构设计提供了必要的上下文和信息。

**集成方式**:
- **产品简报**: 作为PRD工作流的输入
- **市场研究**: 作为PRD的上下文
- **领域研究**: 作为PRD的上下文
- **技术研究**: 作为架构设计的输入

**文档来源**
- [workflows-analysis.md](file://src/modules/bmm/docs/workflows-analysis.md#L170-L182)

### 实现阶段的需求

实现阶段的需求通过架构决策文档传递给AI代理。文档中的决策和模式确保所有代理遵循相同的规则，避免冲突。

**关键活动**:
- 将架构决策文档作为实现阶段的输入
- 确保所有代理遵循文档中的决策和模式
- 通过一致性规则防止代理冲突

**文档来源**
- [workflow-architecture-reference.md](file://src/modules/bmm/docs/workflow-architecture-reference.md#L18-L19)

## 结论

BMAD方法论的架构设计工作流通过八个步骤，从初始化到完成，确保了架构设计的连贯性和可实施性。通过使用`architecture-decision-template.md`定义输出格式和内容要求，`domain-complexity.csv`和`project-types.csv`数据文件影响架构决策过程，以及实际案例分析展示了在不同项目类型中的应用，该工作流能够有效衔接分析阶段的输出和实现阶段的需求，确保架构设计的质量和一致性。
